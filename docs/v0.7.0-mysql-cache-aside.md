# v0.7.0 MySQL Cache-Aside 设计与部署

## 边界与一致性

MySQL 默认关闭，关闭路径不创建线程、不读取密码且不链接客户端库。启用后 MySQL 是
String、Hash、ZSet 和顶层绝对 TTL 的最终数据层，内存 Cache 与现有 RDB/AOF 是热
快照。仅允许本服务修改业务表；v0.7.0 不支持外部 SQL 写入、CDC、binlog 订阅、存储
过程或 AOF rewrite。

命中请求不访问 MySQL。miss 由默认 8 个读线程完整加载一个顶层对象，同 key 请求在
存储层合并。连接挂起期间停用 `EPOLLIN`，但已生成响应仍可发送；完成结果由 eventfd
唤醒 Reactor，连接 ID 代次不匹配的结果会被丢弃。空值缓存默认 3 秒、10,000 key，
所有写命令先失效对应空值。

写响应的耐久边界是本地修改和 AOF 写入，不等待 MySQL。每条实际生效的 canonical
AOF mutation 后紧邻：

```text
PING KVMYSQL1:<32位writer UUID十六进制>:<mutation sequence>
```

单 writer 按 sequence 顺序提交，在同一事务内完成业务表、`kv_change_log` 和
`kv_writer_state` 水位更新。提交结果不确定时先查水位；已应用的 sequence 不重复
执行。LRU 淘汰和 TTL 热快照清理产生的无标记 `DEL` 不删除 MySQL 数据。脏 key 在
MySQL 水位追平前被淘汰后，读请求保持异步挂起，禁止从旧数据库值回填。

## Schema 与账号

服务不会执行 DDL。先以管理员账号创建库并执行版本化 schema：

```bash
sudo apt-get install mysql-server default-libmysqlclient-dev
sudo mysql -e "CREATE DATABASE kvstore CHARACTER SET utf8mb4"
sudo mysql kvstore < config/mysql-v0.7.0.sql
```

再创建仅具业务 DML 权限的服务账号；主机范围和密码按部署环境调整：

```sql
CREATE USER 'kvstore'@'127.0.0.1' IDENTIFIED BY 'replace-me';
GRANT SELECT, INSERT, UPDATE, DELETE ON kvstore.* TO 'kvstore'@'127.0.0.1';
```

密码只通过环境变量传入，避免出现在进程参数中：

```bash
make MYSQL=1
export KVSTORE_MYSQL_PASSWORD='replace-me'
./kvstore --appendonly yes --appendfilename appendonly.aof \
  --appendfsync everysec --mysql yes --mysql-host 127.0.0.1 \
  --mysql-port 3306 --mysql-user kvstore --mysql-database kvstore
```

启动会检查 schema version、bootstrap state 和 SELECT/INSERT/UPDATE/DELETE 权限。
连接、schema、权限或 outbox 对账任一失败时直接退出，不创建监听 socket。

## 配置默认值

| 选项 | 默认值 | 约束 |
| --- | ---: | --- |
| `--mysql` | `no` | `yes` 时必须 `--appendonly yes` |
| `--mysql-host` / `--mysql-port` | `127.0.0.1` / `3306` | TCP 地址 |
| `--mysql-user` / `--mysql-database` | `kvstore` / `kvstore` | 非空 |
| `--mysql-read-workers` | `8` | 1–64 |
| `--mysql-connect-timeout` | `2` 秒 | 正整数 |
| `--mysql-io-timeout` | `2` 秒 | 正整数 |
| `--mysql-read-queue` | `4096` | 请求数上限 |
| `--mysql-write-queue` | `64MiB` | canonical mutation 字节上限 |
| `--mysql-load-max` | `64MiB` | 单顶层 key 完整加载上限 |
| `--mysql-negative-ttl-ms` | `3000` | `0` 禁用空值缓存 |
| `--mysql-negative-capacity` | `10000` | `0` 禁用空值缓存 |

每个读线程和全局 writer 各自独占 MySQL 连接。线程分别调用客户端线程初始化/销毁；
断线后显式重建连接和 prepared statements，不使用自动重连。

## 首次启用与恢复

首次启用允许 `kv_schema_meta.bootstrap_state` 为 `EMPTY`，但 `kv_keys`、writer state
和 change log 必须为空，否则拒绝启动。服务先按既有规则恢复 RDB+AOF，再把所有对象
及绝对毫秒 TTL 灌库。状态先改为 `IN_PROGRESS`，每个对象独立事务提交，全部完成后
设置 `READY`、active writer UUID 和已应用水位。进程在灌库中断后，下一次启动清理
未完成数据并从内存快照安全重试。

常规启动扫描完整 AOF 并取得 writer UUID 和最大 mutation sequence：

- MySQL 水位落后：按标记顺序同步补投缺失 mutation；
- MySQL 水位领先：查询领先 change log 并从热快照删除涉及 key，后续正常回源；
- UUID 不一致、标记格式/顺序错误或 change log 查询失败：拒绝启动。

关闭时最多等待 5 秒排空 writer；剩余 mutation 已存在于 AOF，下一次启动继续补投。
保持现有 RDB 格式，RDB 不保存 MySQL 水位。

## 故障语义与观测

运行期 MySQL 不可用时：未过期内存命中继续服务；miss 返回
`ERR MySQL backend unavailable`；单 key 超限返回
`ERR MySQL object exceeds load limit`；读队列满或写队列达到高水位返回 `TRYAGAIN`。
不会提供已过期数据。

`INFO MYSQL` 返回读/写连接、队列及上限、submitted/applied 水位、loads、同 key 合并、
负缓存命中、读写错误、重连次数和最后一个 MySQL error code。密码、SQL 参数及原始
key/value 不进入该输出。

## 验收与性能报告

真实集成测试至少覆盖三种类型、二进制 key/value/field/member、WRONGTYPE、TTL、
LRU 后回源、冷写返回值、事务回滚、重连、大对象限制、首次灌库、双向水位恢复和
数据库提交前后 `SIGKILL`。MySQL 关闭路径必须通过现有 unit/integration、ASan/UBSan、
Valgrind 与 Helgrind 矩阵。

VMware Ubuntu 正式性能门禁沿用 32 连接、64B value、90% GET/10% SET、P16/P64、
5 轮中位数。MySQL 开启但 100% 命中的 QPS 损失目标不超过 5%、P99 增长不超过
10%；热 key AOF 写回的 QPS 损失目标不超过 10%、P99 增长不超过 20%。报告必须记录
CPU、内存、磁盘、编译选项、客户端位置、请求规模和持续时间；miss、热点合并及断库
只填写实测结果，不预设 QPS 或延迟。

### 全量冷 key MySQL 回源基准

`bench/mysql_cold_miss_bench.py` 专门测量 String 的全量冷 miss。脚本先生成只含
`SET` 的 seed AOF，再由服务启动恢复并通过首次 bootstrap 写入测试库；它不会用 SQL
直接插入业务数据。随后每轮都使用新的空 AOF 启动新进程，因此内存 Cache 从 0 个 key
开始。C 客户端以稳定 key 编号发送不重复的 GET，避免 Python 客户端成为 QPS 瓶颈。

正式测试会清空业务表，数据库名必须以 `_test` 结尾。先确保 9096 端口没有旧服务，
schema 已部署且服务账号具有 DML 权限，然后执行一次小规模 smoke：

```bash
export KVSTORE_MYSQL_TEST_PASSWORD='kvstore_test_only'
export KVSTORE_MYSQL_TEST_HOST='127.0.0.1'
export KVSTORE_MYSQL_TEST_PORT='3306'
export KVSTORE_MYSQL_TEST_USER='kvstore'
export KVSTORE_MYSQL_TEST_DATABASE='kvstore_test'

make MYSQL=1 kvstore mixed_qps_client
python3 bench/mysql_cold_miss_bench.py \
  --requests 10000 --connections 32 --pipeline 1 --repeats 1 \
  --output /tmp/mysql-cold-miss-smoke.csv
```

smoke 通过后，在 VMware Ubuntu 正式环境运行 100 万请求、5 轮：

```bash
python3 bench/mysql_cold_miss_bench.py \
  --requests 1000000 --connections 32 --pipeline 1 --repeats 5 \
  --output bench/result/v0.7.0-mysql-cold-miss.csv
```

也可以通过 Make target 传参：

```bash
KVSTORE_MYSQL_TEST_PASSWORD='kvstore_test_only' \
make mysql-cold-miss-bench \
  MYSQL_COLD_MISS_ARGS='--requests 1000000 --connections 32 --pipeline 1 --repeats 5'
```

脚本每轮强制校验：计时前 Cache key 数为 0、全部 GET 返回 64B value、
`mysql_loads` 增量等于请求数、没有请求合并或回源错误、读队列最终排空。只有全部
条件满足才写入有效结果。输出包括逐轮 CSV、五轮汇总 CSV 和环境 metadata JSON，
终端最后直接打印可用于简历的中位数句子。

正式结果默认使用 `Pipeline=1`，它表达 32 个连接最多 32 个并发回源，并避免将同一
连接内排队时间混入数据库请求延迟。若另测 Pipeline，报告和简历必须明确标注深度，
不同 Pipeline 结果不能混合取中位数。

这里的“全量冷 key”仅指 kvstore 内存 Cache 在每轮开始时为空。MySQL 进程和 InnoDB
buffer pool 不在轮次间重启或清空，因此结果表示常见的“缓存 miss、数据库热缓冲”回源，
不能表述为 MySQL 冷盘读取。

#### 2026-08-22 实测结果

VMware Ubuntu 环境中，客户端、kvstore 与 MySQL 同机运行。MySQL Server 为 8.0.46，
服务使用默认 8 个 reader；负载为 32 连接、Pipeline 1、64B String value 和唯一 key。
10,000 请求 smoke 得到 29,024.98 QPS、P99 1.804 ms，完整校验通过。

正式测试每轮使用 100,000 个唯一 key 和 100,000 次 GET，5 轮结果如下。每轮均通过
空 Cache、返回值、`mysql_loads`、合并、错误和队列排空校验。

| 轮次 | QPS | P99 | 校验 |
| ---: | ---: | ---: | --- |
| 1 | 26,491.81 | 1.965 ms | PASS |
| 2 | 27,525.39 | 1.850 ms | PASS |
| 3 | 26,987.51 | 1.973 ms | PASS |
| 4 | 26,868.13 | 1.901 ms | PASS |
| 5 | 23,343.86 | 2.179 ms | PASS |
| **中位数** | **26,868.13** | **1.965 ms** | **PASS** |

QPS 均值为 26,243.34，范围为 23,343.86–27,525.39，CV 为 5.67%；P99 范围为
1.850–2.179 ms。第 5 轮吞吐明显低于其余轮次，因此保留全部样本并披露波动，不删除
该轮，也不把本结果描述为“CV≤5%”。当前可复述为：

> 在 32 并发、64B value、全量冷 key miss 条件下，MySQL 回源吞吐约 26.9K QPS，
> P99 延迟约 1.97 ms（5 轮中位数，Pipeline=1）。
