# v0.5.1 AOF 优化阶段说明

状态：v0.5.1 发布；功能实现与本地 Linux/WSL 验证已完成。VMware Ubuntu 22.04.5
复验和带完整环境信息的正式性能基线仍需后续补充。

## 本阶段实现

- 新增独立 AOF 模块，使用 RESP2 记录二进制安全写命令。
- 支持 `always/everysec/no` 三种刷盘策略及正常退出收尾。
- TTL 规范化为绝对截止时间，停机不暂停 TTL。
- 启动前流式回放 AOF；自动修复不完整尾帧，拒绝中间损坏与非法命令。
- append/fsync 失败后保护为只读写路径，避免继续扩大未持久化状态。
- 容量淘汰记录显式 DEL，重启恢复不依赖未持久化的 GET/LRU 历史。
- AOF 使用 256 KiB 可复用缓冲区，64 KiB 阈值和 Reactor 事件批次边界合并 write，
  消除逐命令 malloc/free 与逐命令系统调用。
- `everysec` 使用专用后台线程执行 fdatasync；网络、命令与 Cache 仍保持单线程
  Reactor，`always` 继续逐命令同步。
- 新增 AOF 单元测试、后台线程 Helgrind 检查、真实进程重启和成功响应后 SIGKILL
  恢复测试。
- 新增 AOF 纯回放计时、真实进程启动重放基准脚本，以及 mixed benchmark 的可选
  总体/GET/SET 延迟分位数采样和跨刷盘策略多轮编排脚本。

## 本次已执行验证

环境：Windows 主机上的 Linux/WSL，GCC/Make，Makefile 默认
`-std=c11 -O2 -g -Wall -Wextra -Wpedantic`。

```text
make -j2 test             PASS
make -j2 integration-test PASS
make benchmark-test        PASS
make asan                 PASS
make valgrind             PASS（Memcheck 0 errors，无泄漏）
valgrind --tool=helgrind ./test_aof PASS（0 errors）
```

单元测试包括原有 Buffer、旧 KV、RESP、Hash、Cache、服务测试和新增 AOF 测试；
集成测试包括原有 Reactor/Cache 测试、everysec 两次启动恢复，以及 appendfsync no
收到 32 条 Pipeline 成功响应后立即 SIGKILL 并恢复。ThreadSanitizer 可以完成编译，
但在本 WSL 环境启动时报 `unexpected memory mapping`，因此使用 Helgrind 完成线程
竞争检查。

## 优化后 QPS-only 复测

以下为用户在优化后使用 `127.0.0.1` 同机复测的单轮数据：32 条连接、Pipeline
16、共享 100,000 key、90% GET / 10% SET、无 TTL、每连接预热 1,000 次、计时
请求 10,000,000 次，服务端使用 `--maxmemory 64MiB --maxkeys 100000`。本轮未同时
提供 Ubuntu 版本、CPU/内存和编译选项，因此只用于同参数前后对比，不作为正式
发布性能基线。持续时间按请求数除以 QPS 折算。

| AOF 配置 | 持续时间 | QPS |
| --- | ---: | ---: |
| `appendonly no` | 12.720879 s | 786,109.17 |
| `appendonly yes + appendfsync no` | 14.090436 s | 709,701.23 |
| `appendonly yes + appendfsync everysec` | 14.296027 s | 699,495.03 |

相对关闭 AOF，`appendfsync no` 单轮吞吐下降约 9.72%，`everysec` 下降约 11.02%。
与优化前同参数单轮的 575,728.28 和 569,957.03 QPS 相比，两种 AOF 策略分别提升
约 23.27% 和 22.73%，说明复用缓冲、Pipeline 合并 write 与后台 fdatasync 的优化
方向有效。该 QPS-only 测试只有单轮且未采集延迟，只用于和优化前同口径数据对比。

该表没有启用 `-L`，用于观察客户端时间戳和样本存储开销之外的纯 QPS。下面的在线
尾延迟测试启用了 `-L`，两组 QPS 不能直接横向比较。

GCC `-O2`，客户端与服务端通过 `127.0.0.1` 同机运行；32 条连接、Pipeline 16、
共享 100,000 key、90% GET / 10% SET、64B value、无 TTL、每连接预热 1,000 次，
每轮计时 10,000,000 请求并重复 5 轮。以下均为五轮中位数，范围列为五轮最小值到
最大值；本轮 CSV 未附 CPU、内存、磁盘和 Ubuntu 版本，因此仍属于阶段实测。

| AOF 策略 | QPS 中位数 | QPS 范围 | 相对 off | Mean | P50 | P99 中位数 | P99 范围 | P99.9 | P99/P50 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `off` | 763,921.95 | 754,841.02–764,430.76 | — | 659.150 μs | 648.118 μs | 1,004.092 μs | 998.557–1,008.982 μs | 1,089.858 μs | 1.543 |
| `appendfsync no` | 730,769.71 | 718,050.12–749,737.19 | -4.34% | 689.600 μs | 672.381 μs | 1,033.979 μs | 1,019.637–1,060.179 μs | 1,179.229 μs | 1.538 |

相对关闭 AOF，`no/everysec` 的 P99 分别增加约 2.98% 和 4.70%；P99/P50 均维持
约 1.54，主要是整体延迟平移。每轮请求全部完成，GET 命中率 100%，SET 错误为 0。
GET/SET P99 几乎相同是 Pipeline 批次计时定义造成的，不能解释为两类命令服务端
执行时间相同。两种 AOF 策略的最终文件均为 133,166,493 bytes（约 127.0 MiB），
包含计时外预加载和清理，不能直接用于计算计时阶段写带宽。单次 max 达到约
12.8 ms，但 P99.9 仍为约 1.07–1.28 ms，极端值需要结合直方图次数继续分析。

32 条连接乘 Pipeline 16，理论最大在途请求为 512；三种策略用 QPS × mean latency
估算分别约为 503.5、503.9 和 505.0，与闭环 Pipeline 模型一致，也说明该延迟不是
服务端单命令纯执行耗时。

## AOF 启动重放复测

使用 `bench/aof_replay_bench.py` 生成唯一 key、64B value 的 RESP2 `SET` AOF，
每个规模重复 5 次。

| 命令数 | AOF 大小 | 重放中位数 | 重放范围 | 完整启动中位数 | 中位命令吞吐 | 中位字节吞吐 | 峰值 RSS 中位数 | CV |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10,000 | 0.97 MiB | 5.035 ms | 4.889–5.263 ms | 10.785 ms | 1.986M cmd/s | 192.96 MiB/s | 4.29 MiB | 2.84% |
| 100,000 | 9.81 MiB | 54.360 ms | 53.098–57.670 ms | 57.532 ms | 1.840M cmd/s | 180.50 MiB/s | 26.21 MiB | 3.00% |
| 1,000,000 | 99.08 MiB | 780.884 ms | 553.039–997.459 ms | 786.548 ms | 1.281M cmd/s | 126.88 MiB/s | 242.72 MiB | 22.40% |

10,000/100,000 命令的回放 CV 约 3%，基本接近线性；1,000,000 命令 CV 达
22.40%，不能选取最快一轮作为基线。100 万命令时纯回放约占完整启动时间的
99.28%，瓶颈主要在 RESP 解析和 Cache/Hash 重建，而不是 Reactor 初始化。该数据集
每条命令都产生一个存活 key，峰值 RSS 约 255 bytes/key；真实 AOF 的覆盖写、DEL、
TTL 和最终存活 key 数不同，内存与回放时间也会改变。

## 已知限制

- AOF 默认关闭，需使用 `--appendonly yes` 显式开启。
- 不支持 AOF rewrite，文件只增不减。
- 普通文件 write 仍由 Reactor 执行，极慢存储或内核脏页限流可能影响尾延迟。
- `always` 仍逐命令同步；后台线程只用于 everysec，不处理 Cache 或网络。
- 不包含 MySQL、复制、集群或通用后台任务线程。
