# v0.4.0 Release Notes（候选草稿）

> 状态：功能与阶段验收完成，代码仍位于 feature/cache-ttl-lru；尚未合并到
> develop/main，也尚未创建 v0.4.0 tag 或 GitHub Release。

v0.4.0 将 RESP2 epoll 主服务统一为 Hash Cache，并完成动态 Hash、TTL、主动与
惰性过期、精确 LRU、双容量限制、缓存统计以及大 keyspace 混合负载基准。

## 主要变更

- 固定 102,400 桶 Hash 改为从 16 桶开始的动态 Hash，0.75 负载因子触发两倍
  扩容，并使用双表渐进式 rehash。
- 新增 Cache 模块；Hash 负责二进制安全 key 索引，条目保存 value、绝对毫秒
  截止时间、TTL 堆下标和 LRU 指针。
- 新增 SET EX/PX、EXPIRE/PEXPIRE、TTL/PTTL 和 PERSIST。
- Reactor 通过 Linux timerfd 提供通用 100 ms 周期回调；每轮主动过期最多删除
  64 个 key，周期 rehash 最多迁移 16 个旧桶。
- 新增精确 LRU 和 maxmemory/maxkeys 双容量限制；任一超限即从尾部淘汰。
- 新增 INFO CACHE，报告 key、逻辑内存、索引内存、hit/miss、过期、淘汰和
  Hash 状态。
- epoll 服务移除 --engine 并固定使用 Hash；Array、RBTree、旧文本服务与
  NtyCo 只保留在历史接口和回归测试中。
- 新增 mixed_qps_client：共享可配置 keyspace、90% GET / 10% SET、64B value、
  均匀随机访问、可选 TTL，并自动报告客户端命中率和计时区间内的服务端缓存统计。

## 验收工作流

本阶段采用以下顺序，避免把功能错误、资源错误和性能结果混在一起：

~~~text
v0.3.0
  -> feature/cache-ttl-lru
  -> 干净构建和编译告警检查
  -> Hash/Cache/RESP/历史接口单元测试
  -> Reactor 与 Cache 集成测试
  -> ASan/UBSan
  -> Valgrind
  -> NtyCo 历史后端构建回归
  -> 固定环境、固定负载的功能性和性能基准
  -> 更新 README、设计文档和 Release Notes
  -> 提交并推送功能分支
  -> Draft PR 合入 develop
  -> 发布前合入 main 并创建 tag/Release
~~~

性能测试每个场景均重新启动服务，客户端先并行预加载整个 keyspace，再执行预热；
预加载、预热、INFO CACHE 前后快照和清理都不计入 QPS。计时阶段严格包含
90% GET 与 10% SET，所有连接共享 keyspace，并使用固定随机种子保证访问序列可
复现。

## 阶段性能基线

### 环境与公共参数

- VMware Ubuntu 22.04.5，8 核 CPU，12 GB 内存。
- 客户端与服务端同一虚拟机，通过 127.0.0.1:9096 通信。
- Makefile 默认编译参数：-O2 -g -Wall -Wextra -Wpedantic。
- 服务端为单线程 epoll Reactor，无 AOF、数据库或其他持久化路径。
- 32 条持久连接，Pipeline 深度 16，总请求数 10,000,000，每连接预热
  1,000 次。
- 工作集为 100,000 个共享 key，均匀随机访问，value 为 64B，固定随机种子 1。
- maxmemory=64MiB；测试结束由客户端清理 key。

执行模板：

~~~bash
./kvstore --maxmemory 64MiB --maxkeys MAXKEYS

./mixed_qps_client \
  -s 127.0.0.1 -p 9096 \
  -c 32 -n 10000000 -w 1000 -P 16 \
  -k 100000 [-T 5000]
~~~

### 大 keyspace、TTL 与 LRU 结果

| 场景 | maxkeys | TTL | GET 命中率 | expired | evicted | 耗时 | 总 QPS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 大 Hash，全容量命中 | 200,000 | 0 | 100.0000% | 0 | 0 | 13.223161 s | 756,248.82 |
| LRU 容量压力 | 50,000 | 0 | 50.0095% | 0 | 499,785 | 11.682173 s | 856,005.09 |
| TTL 过期压力 | 200,000 | 5,000 ms | 98.5914% | 16,318 | 0 | 13.180664 s | 758,687.11 |
| TTL + LRU 综合压力 | 50,000 | 5,000 ms | 50.0194% | 32 | 499,209 | 12.090706 s | 827,081.56 |

四个场景都完成 9,000,000 次 GET 和 1,000,000 次 SET，set_errors=0。

50,000 容量场景的总 QPS 高于 200,000 容量场景，不代表缓存效果更好。GET miss
返回 5B 的 Null Bulk，而 64B 命中值的 RESP 响应为 71B；miss 也不执行成功
GET 的精确 LRU 链表更新。容量较小时约一半 GET 为更便宜的 miss，常驻条目更少，
且 50,000/131,072 的 Hash 负载因子低于 100,000/131,072，因此总请求 QPS 会
提高。按有效命中 GET 计算，无 TTL 的两个场景分别约为 680,624 hit/s 和
385,275 hit/s，容量充足的场景实际返回了更多有效缓存数据。

TTL 全容量场景在计时期间从 131,072 个 Hash 槽扩容到 262,144。原因是预加载后
的 SET 都是覆盖，不会再次检查插入扩容；TTL 删除产生缺失 key 后，后续 SET
重新插入并触发下一轮渐进式 rehash。该迁移成本已经包含在对应 QPS 中。

### 非 Pipeline 对照

同机、32 连接、90% GET / 10% SET、64B value、每连接预热 1,000 次：

| Pipeline | 请求数 | 工作集 | 耗时 | QPS |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1,000,000 | 32 个连接私有热 key | 14.099517 s | 70,924.42 |
| 16 | 10,000,000 | 32 个连接私有热 key | 10.446373 s | 957,270.08 |

这组数据只用于说明 Pipeline 对同机请求/响应等待和系统调用摊销的影响，不代表
大数据集缓存效果；大 keyspace 四场景才作为 v0.4 Cache 的阶段综合基线。

## 如何解释与复现

- 总 QPS 会把命中、未命中和 SET 都计为一条完成请求，不能脱离命中率单独比较。
- LRU 容量测试应同时记录 get_hit_rate_percent、server_evicted_keys_delta 和
  有效 hit/s。
- TTL 测试应同时记录 server_expired_keys_delta；同一 key 的多次 miss 只对应
  一次实际过期删除，因此 miss 数不等于 expired 数。
- 大 Hash 扩展测试应保证 maxkeys >= keyspace，否则结果同时包含淘汰和更低的
  Hash 负载因子。
- 当前 GET miss 不执行数据库回填；Cache-Aside 回填属于 v0.6，因此本阶段的
  miss 只测空响应和后续随机 SET 重新写入。
- 上表是单轮阶段性记录，尚无延迟 P50/P95/P99，也未重复多轮取中位数；不得作为
  跨项目或生产环境性能结论。

## 已知限制

- 不包含 AOF、MySQL Cache-Aside、配置文件、Hash 缩容、集群或复制。
- maxmemory 是逻辑缓存条目费用，不等同于进程 RSS。
- 主动过期和 rehash 都采用有界增量维护，物理回收可能延后到后续周期。
- 精确 LRU 的每次成功 GET/SET 都会更新双向链表，不等同于 Redis 的近似抽样 LRU。
- mixed_qps_client 当前使用均匀随机分布，尚未提供 Zipf/热点分层和延迟分位数。
